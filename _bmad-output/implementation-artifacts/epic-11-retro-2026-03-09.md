## 2. What Went Well

**Bob (Scrum Master):** Let's start with the positives. What worked well this epic?

### 2.1 Consistent Script Architecture Across All Seeding Stories

**Alice (Dev):** The pattern established in Story 11.1 (`seed_vocabulary.py`) was reused cleanly in 11.2, 11.3, and 11.4. Every seeding script has the same structure:
- `parse_*()` / `extract_*_llm()` — data extraction
- `validate_*()` — schema validation
- `assign_*_order()` — sequential ordering
- `seed_*()` — batch upsert with error handling
- `if __name__ == "__main__":` — CLI with `--dry-run`, `--book`, `--chunks-dir`

This made each subsequent script faster to write and easier to review.

**Dave (Architect):** The `src/scripts/` directory created in 11.1 was a clean architectural decision. Seeding scripts are clearly separated from the API and service layers. The `__init__.py` with a module docstring (required by ruff D104) was a small but important detail.

### 2.2 LLM-Assisted Extraction for OCR'd Content

**Alice (Dev):** Stories 11.2, 11.3, and 11.4 all used LLM-assisted extraction to parse messy OCR'd textbook content. The approach of using `gpt-4o-mini` with `temperature=0.0` for deterministic structured extraction worked well. The prompts were detailed enough to handle OCR noise, numbered sections, and sub-sections.

**Dave (Architect):** The lazy LLM instantiation pattern (create LLM only on first non-dry-run call) was a good fix that came out of code review. It means `--dry-run` works without API keys, which is important for CI and local testing.

### 2.3 Idempotent Upserts Throughout

**Carol (QA):** Every seeding script uses upsert on the UNIQUE constraint, not insert. This means scripts can be run multiple times safely. We verified idempotency for Story 11.1 (the only one with actual data seeded). The pattern is consistent across all four scripts.

### 2.4 Browse Screen Pattern Established in 11.5, Reused in 11.6 and 11.7

**Alice (Dev):** Story 11.5 (Vocabulary Browse) established the mobile browse screen pattern:
- Route at `app/chapter/[chapterId]/[content-type].tsx`
- TanStack Query hook with 30-minute `staleTime` (static textbook content)
- Centralized `queryKeys` factory entry
- `42P01` graceful handling (table doesn't exist yet)
- Co-located component tests

Stories 11.6 and 11.7 followed this pattern exactly. Story 11.6 even proactively added the co-located `GrammarPointCard.test.tsx` because the pattern was established in the 11.5 code review.

**Carol (QA):** Test coverage was strong across all browse screens: loading states, empty states, error states, section grouping, toggle behavior (11.7). The 11.5 code review caught the missing co-located component test pattern, and 11.6/11.7 applied it from the start.

### 2.5 Premade Exercise Adapter Pattern (11.8)

**Dave (Architect):** The `premadeExerciseAdapter.ts` in Story 11.8 is a clean adapter pattern. It transforms the JSONB content schemas into the `QuizQuestion[]` format that all existing exercise components expect. This means zero changes to existing quiz components — the adapter is the only new piece of glue code. The architecture held up well.

### 2.6 Unexpected Discovery: Book 5 Data

**Alice (Dev):** Story 11.1 discovered that `Flash-card.tsv` contains Book 5 data (926 items) in addition to Books 1-4. The script was designed to handle any book number, so it seeded all 5 books automatically. We ended up with 3,997 vocabulary items instead of the expected ~3,073. This is a positive surprise — more data for future quiz generation.

## 3. Challenges and Recurring Issues

**Bob (Scrum Master):** Now let's talk about what was hard. What patterns of issues did we see across stories?

### 3.1 [RECURRING] Missing Quality Threshold for LLM Calls

**Carol (QA):** This was the most common HIGH-severity issue across the LLM-based seeding scripts. Story 11.3 (dialogues) had it fixed in code review. Story 11.4 (premade exercises) had the same issue and needed the same fix. The pattern: very low quality OCR chunks (content_quality < 0.5) were being sent to the LLM, wasting API calls on garbage content.

**Dave (Architect):** The fix is always the same: add `if chunk.get("metadata", {}).get("content_quality", 1.0) < 0.5: continue` before the LLM call. This should have been in the story template for any LLM-based seeding script.

**Action Item:** Add quality threshold check to the seeding script template/pattern documentation so future scripts include it from the start.

### 3.2 [RECURRING] Missing Deduplication Before Upsert

**Carol (QA):** Also recurring in 11.3 and 11.4: when the same `(book_id, lesson_id, dialogue_number)` or `(book_id, lesson_id, exercise_type)` appears in multiple chunks (split OCR pages), the scripts would produce conflicting rows. Both needed a deduplication pass before `assign_*_order()`.

**Dave (Architect):** The fix is always: keep the last extraction per unique key (later chunks = more complete content). This is a known pattern for OCR'd multi-page content.

**Action Item:** Add deduplication logic to the seeding script template for any script that processes chunked content.

### 3.3 [RECURRING] Inline Query Keys Instead of Centralized Factory

**Carol (QA):** Story 11.5 (vocabulary browse) used `['vocabulary', bookId, lessonId]` inline instead of the centralized `queryKeys` factory. This was caught in code review and fixed. Stories 11.6 and 11.7 applied the pattern correctly from the start.

**Dave (Architect):** The `queryKeys.ts` factory is the established pattern for cache invalidation consistency. Any new TanStack Query hook must add its key to the factory.

**Action Item:** Add `queryKeys` factory requirement to the mobile hook dev notes template.

### 3.4 [RECURRING] Missing staleTime for Static Content

**Carol (QA):** Story 11.5 also missed `staleTime` on the vocabulary hook. Vocabulary is static textbook content that never changes during a session, but the hook was refetching on every window focus. Fixed to 30 minutes in code review. Stories 11.6 and 11.7 applied 30-minute staleTime from the start.

**Action Item:** Add `staleTime: 1000 * 60 * 30` as the default for all hooks querying static textbook content (vocabulary, grammar, dialogues, premade exercises).

### 3.5 [RECURRING] Missing Accessibility Attributes on Pressable Cards

**Carol (QA):** Story 11.5's `VocabularyItem` Card was missing `accessibilityRole` and `accessibilityLabel`. The project pattern (ChapterListItem, BookCard) requires these on all pressable cards. Fixed in code review.

**Action Item:** Add accessibility requirements to the component dev notes template. Every pressable Card must have `accessibilityRole` and `accessibilityLabel`.

### 3.6 Dead Code / Unused Functions

**Alice (Dev):** Story 11.3 had `detect_dialogue_number` defined and tested but never called — it was dead code. The function was useful but only activated as a fallback after the code review fix. Story 11.1 had an unused `warnings` list in `_print_summary`.

**Dave (Architect):** This is a common issue when implementing complex extraction logic. The fix is to ensure every function is either called or explicitly marked as a future hook.

### 3.7 Documentation vs. Reality Mismatch (UNIQUE Constraints)

**Alice (Dev):** Story 11.1's dev notes documented the UNIQUE constraint as `(book_id, lesson_id, vocab_section, sort_order)` but the actual DB constraint was `(book_id, lesson_id, vocab_section, traditional)`. Story 11.2's story file documented `UNIQUE (book_id, lesson_id, grammar_order, sort_order)` but the actual constraint is `UNIQUE (book_id, lesson_id, grammar_order)`. Both were caught in code review.

**Dave (Architect):** The source of truth for UNIQUE constraints is the live Supabase DB, not the story documentation. We should always verify against the DB before writing upsert logic.

**Action Item:** Add a step to the seeding script workflow: verify UNIQUE constraints against live DB before implementing upsert logic.

### 3.8 Navigation Entry Points Deferred (Stories 11.5, 11.6, 11.7)

**Maxime (PO):** Stories 11.5, 11.6, and 11.7 all had Task 5 (navigation from Exercise Type Selection) skipped because Story 3.5 wasn't implemented yet. The browse screens exist but aren't reachable from the main navigation flow.

**Dave (Architect):** This is a dependency ordering issue. Story 3.5 (Exercise Type Selection) is done, so the navigation wiring can happen now. But it wasn't included in Epic 11 because the stories were written before 3.5 was complete.

**Action Item:** Wire navigation from Story 3.5 to the three browse screens (vocabulary, grammar, dialogues) as part of the next sprint's cleanup tasks.

## 4. Lessons Learned

**Bob (Scrum Master):** What are the key lessons we're taking forward?

### 4.1 Establish Patterns Early, Document Them Explicitly

**Dave (Architect):** The seeding script pattern (quality threshold, deduplication, lazy LLM, batch upsert) should have been documented in Story 11.1's dev notes as "required for all LLM-based seeding scripts." Instead, it was discovered through code review in 11.3 and 11.4. The pattern is now clear — document it for future seeding work.

### 4.2 Code Review Catches Systemic Issues, Not Just Story-Specific Bugs

**Carol (QA):** The adversarial code review process caught 5-6 issues per story, many of them systemic (quality threshold, deduplication, accessibility, query keys). The review process is working well. The key insight: when a reviewer finds the same issue in multiple stories, it should trigger a template update, not just a per-story fix.

### 4.3 LLM Extraction is Powerful but Requires Defensive Coding

**Alice (Dev):** LLM extraction for OCR'd content works well, but requires:
1. Quality threshold to skip garbage input
2. JSON parsing with fallback (markdown code block stripping)
3. Schema validation of LLM output (not just type checking — validate structure)
4. Rate limiting between API calls
5. Lazy instantiation (don't create LLM client in dry-run mode)

All five of these were either in the original implementation or added in code review. Future LLM extraction scripts should include all five from the start.

### 4.4 The Adapter Pattern Scales Well for Exercise Types

**Dave (Architect):** Story 11.8's `premadeExerciseAdapter.ts` is a clean solution to the "same UI, different data source" problem. The adapter transforms premade JSONB content into the same `QuizQuestion[]` format as AI-generated quizzes. This means zero changes to existing quiz components. The pattern should be reused if we add other content sources in the future.

### 4.5 Static Content Hooks Need Different Cache Settings

**Alice (Dev):** Textbook content (vocabulary, grammar, dialogues, premade exercises) is static — it never changes during a user session. These hooks should always use `staleTime: 1000 * 60 * 30` (30 minutes) or higher. Dynamic content (quiz results, progress) should use shorter or no staleTime. This distinction should be in the hook template.

### 4.6 Book 5 Data Was a Surprise — Plan for Extensibility

**Maxime (PO):** We expected Books 1-4 but got Books 1-5. The seeding scripts handled this gracefully because they don't hardcode book numbers. This is good design. Future scripts should always be written to handle any book number, not just the currently known set.
