## 2. What Went Well

**Bob (Scrum Master):** Let's start with the positives. What worked well this epic?

### 2.1 Clean Component Architecture from Story 3.1

**Charlie (Senior Dev):** Story 3.1 established a solid component architecture that held up through all 7 stories. The `components/chapter/` directory, `hooks/` pattern, `constants/` for static data, and `types/chapter.ts` for shared interfaces — all of these were defined in 3.1 and reused cleanly in 3.2 through 3.7. No architectural rework was needed.

**Alice (Product Owner):** The decision to put static chapter data in `constants/chapters.ts` (not fetched from an API) was the right call. It made the chapter list screen instant — no loading state needed for the chapter list itself, only for progress data.

### 2.2 Graceful Degradation Pattern for Missing Tables

**Dana (QA Engineer):** Every hook that queries Supabase tables that might not exist yet (chapter_progress, exercise_type_progress, premade_exercises, vocabulary, grammar_points, dialogues) handles the `42P01` error code gracefully — returning empty data instead of crashing. This pattern was established in Story 3.1 and applied consistently through 3.7.

**Charlie (Senior Dev):** This was critical because Epic 3 was implemented before Epic 6 (progress tracking) and Epic 11 (content seeding). The app needed to work with zero data in those tables. The graceful degradation pattern made that possible.

### 2.3 Open Navigation Philosophy Enforced Consistently

**Alice (Product Owner):** Story 3.4 established the "no gates" principle explicitly, and it was respected throughout. No chapter has a lock icon, no prerequisite checks, no "complete Chapter X first" messages. The `ChapterListItem` component has no conditional `onPress` logic — it's always enabled. This aligns with the Dangdai curriculum philosophy where users know what they need to study.

**Dana (QA Engineer):** Story 3.4 even added explicit "no gating" unit tests to `ChapterListItem.test.tsx` — 5 tests that verify the absence of lock logic. That's a good pattern: test for what should NOT be there.

### 2.4 Progress State Visual Design (3 States)

**Charlie (Senior Dev):** The three-state progress system in Story 3.3 — not-started (gray), in-progress (blue + progress bar), mastered (green + checkmark) — is clean and immediately understandable. The color tokens ($gray4/$blue4/$green4 for badges, $gray12/$blue11/$green11 for text) are consistent with the Tamagui theme system.

**Dana (QA Engineer):** The percentage bounds validation (clamping to [0, 100]) added in the 3.3 code review was a good defensive measure. Progress data from the DB could theoretically be out of range.

### 2.5 Exercise Type Selection Screen (Story 3.5) — Scope Expansion Done Well

**Alice (Product Owner):** Story 3.5 was the most complex story in the epic. It replaced the simple vocabulary/grammar two-button screen from Story 3.4 with a full 8-card grid (Mixed + 7 exercise types) plus a premade exercises section. The scope expansion was handled cleanly — the new `exercises.tsx` route replaced the old `quiz/[chapterId].tsx` as the navigation entry point, and the chapter list was updated to point to the new route.

**Charlie (Senior Dev):** The Rules of Hooks fix in Story 3.5 code review was important — the initial implementation had a conditional hook call that violated React's rules. The fix (always call hooks unconditionally, use the result conditionally) is the correct pattern and was applied correctly in Story 3.7 as well.

### 2.6 Story 3.6 Was a Verification Story Done Right

**Bob (Scrum Master):** Story 3.6 (Expand Book Selection to Books 1-4) is a good example of a verification story. The constants already had all 4 books. The UI was already dynamic. The story's value was in writing the tests that prove it works and fixing a pre-existing bug (wrong chapter title in `useChapters.test.ts`).

**Dana (QA Engineer):** 22 new tests in `books.test.tsx` covering all 4 ACs. That's the right outcome for a verification story — not new code, but test coverage that proves the existing code is correct.

### 2.7 Story 3.7 Closed the Epic 11 Retro Action Item

**Charlie (Senior Dev):** Story 3.7 directly addressed Action Item A7 from the Epic 11 retrospective: "Wire navigation from Story 3.5 to vocabulary/grammar/dialogue browse screens." The story was created specifically to close that action item, and it did so cleanly with conditional visibility (content-aware browse buttons) rather than always-visible buttons.

**Alice (Product Owner):** The count hook pattern (`useVocabularyCount`, `useGrammarPointsCount`, `useDialoguesCount`) using `{ count: 'exact', head: true }` is efficient — it's a HEAD query that returns only the count metadata, not the actual rows. Good for a visibility check.

## 3. What Could Be Improved

**Bob (Scrum Master):** Now let's talk about what was hard or what we'd do differently.

### 3.1 [RECURRING] Code Review Catching Issues That Should Be in Templates

**Dana (QA Engineer):** Across Stories 3.1 through 3.4, code review caught issues that should have been in the story templates from the start:
- Story 3.1: Missing co-located unit tests (HIGH), query key race condition with empty string fallback (HIGH), wrong border radius (MEDIUM), missing skeleton loading state (MEDIUM)
- Story 3.2: Compiled Playwright test files tracked in git (HIGH), missing accessibility label for Chinese title (LOW)
- Story 3.3: No integration test for Chapter List screen (HIGH), missing error state UI (MEDIUM), no bounds validation on percentage (MEDIUM)
- Story 3.4: Missing tests for `loading.tsx` (MEDIUM), invalid chapterId handling (MEDIUM)

**Charlie (Senior Dev):** The pattern is clear: co-located unit tests, accessibility attributes, error state UI, and input validation are consistently missed in the initial implementation and caught in code review. These should be in the story template as explicit checklist items.

### 3.2 [RECURRING] Query Key Race Conditions and Empty String Fallbacks

**Charlie (Senior Dev):** Story 3.1's `useBooks` hook initially used `queryKeys.books(user?.id ?? '')` — an empty string fallback when the user is null. This creates a cache key `['books', '']` that could cache data incorrectly. The fix was to use a different key pattern when user is null. This same pattern risk exists in `useChapterProgress` (Story 3.3) which uses `queryKeys.chapterProgress(user?.id ?? '', bookId)`.

**Dana (QA Engineer):** The correct pattern is to use `enabled: !!user` to prevent the query from running when user is null, AND to use a stable key that doesn't include an empty string. Both conditions together prevent the race condition.

### 3.3 Pre-existing Test Failures Accumulating

**Dana (QA Engineer):** By Story 3.7, there were 5 pre-existing failing test suites unrelated to the story being implemented. These failures were noted in each story's completion notes but not fixed. They're accumulating technical debt in the test suite.

**Alice (Product Owner):** The failures are due to Supabase env vars not being set in the test environment, CompletionScreen UI changes, and exercises navigation changes. These need to be addressed before they mask real regressions.

### 3.4 Chapter Titles Are Placeholder Data

**Alice (Product Owner):** The chapter titles in `constants/chapters.ts` are placeholder English translations (e.g., "Greetings", "Names", "Numbers") and simplified Chinese (e.g., "问候", "名字"). The actual Dangdai textbook uses Traditional Chinese and has specific lesson titles. Story 3.2's dev notes explicitly flagged this: "These are placeholder titles. Replace with actual Dangdai textbook chapter titles when available."

**Charlie (Senior Dev):** This is a content gap, not a code gap. The structure is correct (54 chapters, correct IDs, correct book assignments). The titles need to be updated with actual curriculum data once we have it.

### 3.5 E2E Tests Skipped Due to Missing Test Credentials

**Dana (QA Engineer):** Stories 3.1 through 3.4 all have Playwright E2E tests that are skipped because `TEST_USER_EMAIL` and `TEST_USER_PASSWORD` environment variables aren't set. The tests exist but don't run in CI. This means the full navigation flow (Books → Chapter List → Chapter Detail → Quiz Loading) has never been tested end-to-end in an automated way.

**Bob (Scrum Master):** This is a CI configuration gap. We need test credentials set up in the GitHub Actions environment.

### 3.6 Story 3.5 Had Pre-existing Test Failures at Completion

**Dana (QA Engineer):** Story 3.5's completion notes mention "2 pre-existing failures unrelated to this story." These were not investigated or fixed. The pattern of noting pre-existing failures without addressing them is becoming a habit.

## 4. Key Lessons Learned

**Bob (Scrum Master):** What are the numbered lessons we're taking forward?

### 4.1 Static Data in Constants Is the Right Pattern for Curriculum Content

**Charlie (Senior Dev):** The decision to put all 54 chapters in `constants/chapters.ts` as static TypeScript data (not fetched from an API) was correct. It makes the chapter list screen instant, eliminates a network dependency, and makes the data type-safe. The same pattern should be used for any curriculum metadata that doesn't change per-user.

### 4.2 Three-State Progress Visualization Is the Right UX Pattern

**Alice (Product Owner):** The not-started / in-progress / mastered three-state system (gray / blue+bar / green+checkmark) is clear and immediately understandable. It should be the standard for any progress indicator in the app — chapter progress, exercise type progress, vocabulary mastery, etc.

### 4.3 Graceful Degradation for Missing Tables Is Non-Negotiable

**Charlie (Senior Dev):** Every Supabase query that touches a table that might not exist yet must handle `42P01` gracefully. The pattern is: catch the error, check `error.code === '42P01'`, log a warning, return empty data. This was applied consistently in Epic 3 and should be in every hook template.

### 4.4 Open Navigation Requires Explicit Anti-Pattern Tests

**Dana (QA Engineer):** Story 3.4 added 5 unit tests that verify the ABSENCE of lock logic in `ChapterListItem`. This is a good pattern for "thou shalt not" requirements — test that the forbidden behavior doesn't exist, not just that the desired behavior does.

### 4.5 Rules of Hooks Must Be Enforced at Code Review

**Charlie (Senior Dev):** Story 3.5 had a conditional hook call that violated React's Rules of Hooks. This was caught in code review. The rule is simple: all hooks must be called unconditionally at the top of the component, before any early returns or conditional logic. This should be an explicit code review checklist item.

### 4.6 Verification Stories Need Tests, Not Code

**Bob (Scrum Master):** Story 3.6 is a model for verification stories. When the code already works, the story's value is in writing tests that prove it works and fixing any bugs found during verification. Don't add unnecessary code to a verification story.

### 4.7 Count Hooks for Content Availability Are Efficient

**Charlie (Senior Dev):** The `{ count: 'exact', head: true }` pattern for checking content existence (Story 3.7) is efficient — it's a HEAD request that returns only the count, not the rows. Use this pattern whenever you need to check "does content exist?" without fetching the content itself.

### 8.2 Chapter ID Convention

Chapter IDs follow `bookId * 100 + chapterNumber`:
- Book 1: 101–115 (15 chapters)
- Book 2: 201–215 (15 chapters)
- Book 3: 301–312 (12 chapters)
- Book 4: 401–412 (12 chapters)

Total: 54 chapters across 4 books.

### 8.3 Progress State Thresholds

- **Not started:** `completionPercentage === 0` → gray badge, no progress bar
- **In progress:** `1 ≤ completionPercentage < 80` → blue badge, blue progress bar
- **Mastered:** `completionPercentage >= 80` → green badge, checkmark icon, "Mastered" text

Mastery is never downgraded — `chapter_progress.completion_percentage` stores the BEST score.

### 8.7 Anti-Patterns Established in Epic 3 (DO NOT DO)

- **DO NOT** add chapter locking/gating logic anywhere in the navigation flow
- **DO NOT** fetch chapter list data from API (use `constants/chapters.ts`)
- **DO NOT** use inline query key arrays — always use `queryKeys` factory in `lib/queryKeys.ts`
- **DO NOT** use empty string fallback in query keys (`user?.id ?? ''`) — use `enabled: !!user`
- **DO NOT** call hooks conditionally — all hooks must be called unconditionally (Rules of Hooks)
- **DO NOT** use hardcoded hex colors — use Tamagui theme tokens only
- **DO NOT** skip `42P01` error handling for tables that may not exist yet
